# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Lex Talionis** is a Fire Emblem fangame engine (pygame runtime) plus **LT-maker**, a PyQt5 graphical editor built on top of it. A game is a `.ltproj` directory of JSON data + resources; the engine loads one and plays it, the editor mutates one. The sample project `default.ltproj` (Sacred Stones) ships in-repo.

## Commands

- Run the editor: `python run_editor.py`
- Run the engine on a project: `python run_engine.py` (auto-finds a `*.ltproj` in the repo root)
- Run the map maker: `python run_map_maker.py`
- Run all tests: `python utilities/build_tools/run_tests_parallel.py` — every test module, spread over 8 processes (about 30s, against a few minutes serially). Arguments filter by module name (`run_tests_parallel.py city turn`), `-j N` sets the process count, `--slowest N` lists the slow modules. Only failing modules print their output.
- Run all tests serially: `python -m unittest discover -s app/tests -p 'test*.py'` (wrapper: `./utilities/build_tools/run_tests.sh`)
- Run one test module: `python -m unittest app.tests.test_engine`
- Build docs: `./docs/make.bat html` (output in `_build/html`)
- Install dev deps: `pip install -r requirements_dev.txt` (engine-only: `requirements_engine.txt`, editor: `requirements_editor.txt`). Python + PyQt5 + pygame-ce.

`LT_PROFILE=1` env var enables per-frame timing prints in `driver.py`; `LT_PROFILE_THRESHOLD=<ms>` only prints slow frames.

## Codegen — read this before editing components or event commands

`app/engine/codegen/source_generator.py::generate_all()` runs at startup (both entry points) when not a built release. It generates source files; **do not hand-edit generated files**, edit the inputs:

- `compile_item_system()` / `compile_skill_system()` / `compile_building_system()` scan `app/engine/item_components/*`, `app/engine/skill_components/*`, `app/engine/building_components/*` and emit the dispatch modules `app/engine/item_system.py`, `app/engine/skill_system.py`, `app/engine/building_system.py`.
- `generate_event_command_python_wrappers()` emits Python wrappers for event commands.

🔴 **`item_system.py`, `skill_system.py`, and `building_system.py` are 100% generated and rewritten at runtime** (each opens with a "DO NOT EDIT — generated" banner). An edit you make directly to one of these is silently clobbered the next time the engine/editor starts. Each is assembled from two source inputs you *do* edit: a hand-written base (`component_system/<name>_system_base.py` — holds imports, `Defaults`, and any hand-written dispatch like `condition`/`available`/`target_restrict`) that is copied verbatim into the top, plus the per-hook functions emitted from the `*_HOOKS` table and generator in `component_system/compile_<name>_system.py`. So: add/change a hand-written dispatch fn or shared import → edit `*_system_base.py`; add/change a declarative component hook (name, args, resolution policy) → edit `compile_<name>_system.py`. Then **regenerate** with `python -m app.engine.codegen.source_generator` and commit the regenerated `*_system.py` alongside the source change (the generator is idempotent — regenerating with no source change is a no-op, and does not touch the file: every generator writes through `codegen_utils.GeneratedSource`, which compares before writing. A plain `open(path, 'w')` empties the file first, and with tests running in several processes another one imported it empty).

If you add or change a component hook method and the engine doesn't pick it up, the generated dispatch file is stale — rerun `python -m app.engine.codegen.source_generator`.

## Architecture

Three top-level halves under `app/`:

- **`app/engine/`** — the runtime game (pygame). Entry: `driver.start()` then `driver.run(game)`, a fixed loop pulling input → `game.state.update()` → blit. The whole game is a singleton `GameState` (`game_state.py`) holding every registry (units, items, skills, regions, parties, teams, vars). Control flow is a **stack-based state machine** (`state_machine.py`, `state.py`); states are registered by string nid in `StateMachine.load_states` and pushed/popped (`game.state.change/back`). Combat lives in `app/engine/combat/` driven by a `solver` producing a `playback` log that map/animation combat replay. Live game objects are in `app/engine/objects/` (UnitObject, ItemObject, SkillObject, etc.) — these wrap the static DB prefabs with per-playthrough state.

- **`app/data/`** — the project data model and (de)serialization. Two global singletons: `DB` (`app/data/database/database.py`) for game design data and `RESOURCES` (`app/data/resources/resources.py`) for assets. Both `.load(path, version)` a `.ltproj`. On-disk format is versioned JSON; migration logic is in `app/data/serialization/` (`versions.py`, `migrators/`, `loaders/`). `CURRENT_SERIALIZATION_VERSION` gates load behavior. Validation in `app/data/validation/`; a project with `has_fatal_errors` refuses to launch.

- **`app/editor/`** — PyQt5 editor. One sub-package per data type (e.g. `item_editor/`, `class_editor/`, `event_editor/`), each typically a `*_tab.py` (Qt view), `*_model.py` (Qt model over the DB), and `*_properties.py` (the edit form). `main_editor.py` is the window. Editor state lives in `app/editor/lib/state_editor/`. The editor edits `DB`/`RESOURCES` in memory and serializes back to the `.ltproj`.

Also: **`app/events/`** — the eventing/scripting system, including a custom Python-eventing compiler under `app/events/python_eventing/` (analyzer → compiler → postcomp) that turns user event scripts into runnable code. Event triggers are defined in `app/events/triggers.py` (chapter start/end, unit death, talk, level up, etc.) and matched against `EventPrefab.triggers` at runtime. **`app/map_maker/`** — a separate procedural tile-map tool, with its own palette pipeline (see `app/map_maker/README.md`). **`app/engine/roam/`** — a free-roam exploration mode (town menus, NPC interactions) that runs as its own state machine alongside but separate from tactical map states; **`app/engine/overworld/`** — the node-based overworld graph (map selection, cinematics, route branching).

### Save / restart system

`app/engine/save.py` keeps **two parallel slot listings**: `SAVE_SLOTS` (the Load Game menu) and `RESTART_SLOTS` (the Restart Level menu). They are different files — `-{N}.p` vs `-restart{N}.p` — so a save can appear in one menu but not the other. Restart files are **slot-keyed** and seeded only at new game (the lone `kind=='start'` save in `title_screen.build_new_game`); every later save in `save_io` just **copies the restart file forward** from the slot you loaded into (`old_slot`) to the slot you save into. There is no per-chapter 'start' save.

Gotcha: **"Test Chapter"** (editor → engine via `game_state.start_level()`) bypasses new game entirely — it writes no 'start' save and leaves `current_save_slot = None`. So a first in-session save (e.g. a base/prep save) has no restart file to carry forward; `save_io` falls back to seeding the restart from that save, which is *not* a pristine chapter start. Preload saves (also `kind=='start'` only) are likewise never produced in a Test Chapter session.

A save outlives the shape of the project that made it, since it refers to the DB by nid. Restore raises **`StaleSaveError`** (`app/engine/stale_save.py`) with a "no class with that nid was found in the database" style message when a save names a class, AI, weapon type (in a `ComponentType.WeaponType` item component) or tilemap the project no longer has — those used to crash later, far from the cause. Items and skills missing from the DB deliberately fall back to placeholders, and a missing overworld is skipped. `test_save_round_trip.py` covers both kinds.

### Component system

Items and skills are composed of **components**, not subclasses. A component (e.g. in `app/engine/item_components/formula_components.py`) declares `nid`, `tag`, an `expose` type for its editor field, and implements named **hook methods** like `damage_formula(unit, item)` or `on_hit(...)`. The codegen step collects all components and builds `item_system`/`skill_system` dispatch functions that fan a hook call out across whatever components an item/skill carries. To add a behavior: add a component class with the right hook method name, then regenerate. `item_component_access.py` / `skill_component_access.py` expose the catalogs.

Each hook method has a **resolution policy** controlling how multiple components' return values combine: `ALL_DEFAULT_FALSE` (any False → False; e.g., `is_weapon`), `UNIQUE` (last-defined wins; e.g., `damage_formula`), `NUMERIC_ACCUM` (sum all numerics; e.g., `modify_damage`), `UNION` (merge all returned sets; e.g., `target_icon`). The policy is the `HookInfo(args, ResolvePolicy.X)` value of the hook's entry in `ITEM_HOOKS` / `SKILL_HOOKS` (`app/engine/component_system/compile_*_system.py`) — pick the right one when adding a new hook.

### Aura system

An aura is a parent skill (carrying the Aura component) plus a shared **subskill** object that gets applied to every affected unit — one `SkillObject` instance, one uid, sitting in many units' skill lists at once. Affected units are tracked **only** by board bookkeeping (`game_board.known_auras` / `aura_grid`), never an explicit "who has my aura" list. `aura_funcs.py` is the whole system: `propagate_aura`/`release_aura` (source moves/leaves), `pull_auras` (a unit arrives), `repopulate_aura` (board rebuild on load).

Teardown must be **authoritative**, not board-derived. When a unit leaves the map it drops *all* its AURA-sourced skills (`aura_funcs.remove_all_auras`, called from `game.leave`) by walking its own skill list — a board-position lookup is fragile because `reset_aura` clears board state but not unit skill lists, so re-propagation / teardown ordering / save-load can desync the two and orphan a child skill. AURA `source_type` is non-removable and non-displaceable ([source_type.py](app/engine/source_type.py)): removable only via its exact source uid (the live parent skill instance). Aura children are therefore **not serialized** (`UnitObject.save`/`restore` filter `SourceType.AURA`); they're re-derived from the live board after units arrive on load (`game.load_level` → `pull_auras`) so each child's source points at the current parent. Skip this and a game-over restart restores children with a stale parent uid → unremovable forever (the "permanent aura skill" bug).

### Combat cleanup ordering

`SimpleCombat` (in `combat/simple_combat.py`) resolves and applies hit actions up front (`_apply_actions`, where `on_hit` decrements land), then runs **two cleanup phases on separate frames**: `clean_up1` (`post_combat` state) → `cleanup_combat()`, `handle_unusable_items`, `handle_broken_items`, exp; then `clean_up2` (`exp_pause`) → `handle_state_stack`, `end_combat()`. **Gotcha: `end_combat` runs *after* the broken/unusable checks.** A per-combat consumption that must gate `is_broken`/`is_unusable` — the `one_loss_per_combat` / `one_*_cost_per_combat` deferral in `usable_components.py` (`Uses`, `ChapterUses`, `HPCost`, `ManaCost`, …) — must apply in the **`cleanup_combat` hook** (fires before the checks), *not* `end_combat`; otherwise the item isn't flagged broken/unusable until the next combat (and a promotion-style cancel then mishandles the still-present item). Combat class tree: `SimpleCombat` (base) ← `MapCombat`, and `SimpleCombat` ← `BaseCombat` ← `AnimationCombat`. `BaseCombat.cleanup_combat` **overrides** `SimpleCombat`'s, so it must itself call `item_system.cleanup_combat` or `AnimationCombat` silently skips item cleanup hooks.

### Caching (LTCache) — invalidate *after* mutating component state

`app/engine/utils/ltcache.py`: `@ltcached` wraps a function in `lru_cache` and clears that cache whenever a global "state" uuid changes; the uuid is bumped by `game.on_alter_game_state()`. The cache key is the function's **args** (a `SkillObject`/`UnitObject`, hashed by identity/uid) — it does **not** see a component's mutable internal state. Stateful conditional components (`CombatCondition._condition`, `Nihil._condition` in `skill_components/`) therefore "publish" their state to the cache by calling `game.on_alter_game_state()`. **Gotcha: invalidate *after* writing the state variable, not only before.** `skill_system.condition` is `@ltcached`, and evaluating a combat-condition string re-enters it (a condition referencing `item_system.weapon_type`/`weapon_triangle_override` routes through `item_override` → `condition`). So invalidating before setting `_condition` re-caches the **stale** value under the freshly-bumped state, and it sticks until some unrelated hook bumps state again — e.g. a Weapon-Triangle item-override silently failed to apply on the first hit and "course-corrected" mid-combat. `combat_calcs.compute_advantage` is also `@ltcached` and depends on item overrides, so it inherits the same staleness window.

### 4X building / city system (`avalon` branch, WIP — untested)

A new 4X-genre layer (`git log master..avalon`). **Not yet fully tested; expect rough edges.** Treat as scaffolding.

**Buildings** are component-composed exactly like items/skills (own parallel of the whole component machinery): prefab `BuildingPrefab` + catalog in `app/data/database/buildings.py` (`DB.buildings`), component base `app/data/database/building_components.py` (`BuildingComponent`, `BuildingTags` = BASE/RESOURCE/UNIT/…), concrete components in `app/engine/building_components/base_components.py` (Cost, Requires, LevelIncrease, UpgradesTo, RequiresTerrain, StatChange, ResourcePerTurn, InfluenceBonus, HasEventRegion, HasSkillRegion). Catalog access via `app/engine/building_component_access.py` (`get_building_components`/`restore_component`). Runtime instance is `app/engine/objects/building.py::BuildingObject` (uid-keyed, `next_uid` starts at 100, components copied per-instance like SkillObject). Dispatch is codegen'd just like item/skill: `compile_building_system()` (in `source_generator.generate_all`) copies `component_system/building_system_base.py` + emits hooks from `BUILDING_HOOKS` into `component_system/building_system.py`.

🔴 **`building_system` mirrors `skill_system`: the *city* is the primary object (like `unit`), so every hook is `building_system.foo(city, …)` with `city` first, and a hook coalesces over *every component of every building in the city*.** The parent `building` is **not** passed to the component method — a component reaches its own building via `self.building`, exactly as skill components use `self.skill` and skill dispatch passes `unit` not `skill`. Component method sigs are therefore `(self, city, …)`. (Don't "standardize" by passing `building` explicitly — that's backwards and was corrected mid-session.) There are **two hook shapes**:
- **City-aggregate** (loop all `city.buildings`): declared in `BUILDING_HOOKS` and code-generated — `on_upkeep` (NO_RETURN), `produces_units` (LIST → list-of-lists, flatten in caller), `influence_range_modification` (NUMERIC_ACCUM), and two asked about a unit the city has just drafted: `starting_level_modification(city, unit)` (NUMERIC_ACCUM) and `stat_change(city, unit)` (LIST of `{stat: bonus}` dicts, summed in the caller). `city_funcs.apply_building_bonuses` applies both in `draft_unit` *before* `RegisterUnit`, so they are part of the unit's initial state rather than reversible actions; extra levels go through `unit_funcs.auto_level` (real level-ups, not just a bigger number) and both clamp to the class's max level / max stats.
- **Single-candidate-building** (evaluate one building not yet in the city): **hand-written in `building_system_base.py`**, looping only that building's components, like `condition(building, city)` (`@ltcached`, gates everything) — `available(building, city)`, `target_restrict(building, city, position)`. These take the building explicitly because it isn't in `city.buildings` yet.

Other base hooks: `init`, `after_add(city, building)`, `after_remove(city, building)`.

**Cities**: prefab `app/data/cities.py::City` (placed on a level via `Level.cities`, painted in editor `level_editor/city_painter_menu.py`); runtime `app/engine/objects/city.py::CityObject(City)` carries the mutable 4X state — `population`, `food`, `production` (resources), team-owned `gold` (on the *team*, not the city), `influence` range (`City.contains`/`get_all_positions` are Manhattan-radius), `buildings` (list of BuildingObject), `inn` (stationed unit nids). `food`/`production` are **stores spent when buying** units/buildings — there is no per-turn resource upkeep, no production queue, and no food-driven population growth. `produced_this_turn` enforces **one purchase per city per turn** (a unit *or* a building, not both); `city_funcs.can_purchase`/`mark_purchase` read and flip it, and `run_city_upkeep` clears it. Editor model: `editor/building_editor/building_model.py`. The **City prefab** also carries `buildings: List[[building_nid, position]]` — the editor placements assigned in the Cities tab (`CityBuildingList` widget in `city_painter_menu.py`, drawn on the map by `NewMapView.paint_cities`); `CityObject.from_prefab` instantiates a `BuildingObject` per placement (sets position, registers). **Gotcha: JSON has no tuples** — `City.position` and the placement positions come back as **lists** on load, so `City.restore_attr` coerces them to tuples (otherwise `position == (x,y)` checks in the map view silently fail until an edit rewrites them).

**Registries & persistence**: `GameState` adds `building_registry` (uid→BuildingObject) and `city_registry` (nid→CityObject), with `register_building`/`register_city`, `cities` property, `get_city`. Both saved in `GameState.save`/restored in `load`; in `start_level` each `level.cities` **prefab** is converted via `CityObject.from_prefab` and registered (along with its buildings) — `LevelObject.from_prefab` does *not* convert cities, so `level.cities` is still raw City prefabs. **`building_registry` is a built-once pool** — `register_building` adds on first creation and **`unregister_building` is never called by the engine** (a removed / turnwheel'd-back building stays registered so it's cheap to find again going forward). A building's actual *on-the-map* state is membership in a city's `buildings` list with a non-`None` `position`, toggled by `AddBuilding`/`RemoveBuilding`; derive placement from `game.cities → city.buildings`, **never from `building_registry` membership**. A building that leaves its city **keeps its `position`**, so "registered and positioned" is not "on the map" either: `MapView` once drew from `game.buildings` and kept painting removed, upgraded-away and razed buildings. **Buildings serialize by uid reference from the city** (`CityObject.save` stores `[b.uid …]`; restore resolves via `game.get_building(uid)`). **Actions** (`action.py`): `AddBuilding`/`RemoveBuilding` (call `building_system.after_add/after_remove`, auto-register), `ChangeCityFood`, `ChangeCityProduction`, `ChangeTeamGold`, `ChangeCityPopulation`, `SetCityProduced` — all reversible (turnwheel-compatible). `population` only moves via `ChangeCityPopulation` (events); nothing grows it automatically. Resource income runs through `ResourcePerTurn.on_upkeep(city)` (every building produces — buildings are always "worked"). Higher-level city logic (draftable/buildable queries, valid placement, purchase helpers `get_unit_cost`/`get_building_cost`/`can_afford`/`pay_costs`/`draft_unit`, `run_city_upkeep`) lives in `app/engine/city_funcs.py`; per-turn income is driven from `StatusUpkeepState`: at the start of **each team's own phase** that team pays unit upkeep, then its cities collect income and get their one purchase back.

🔴 **An Action field that holds a CityObject / TeamObject / BuildingObject must be resolvable by `Action.save_obj`/`restore_obj`** (`action.py`) — they now resolve `('city', nid)→game.get_city`, `('team', nid)→game.teams.get`, `('building', uid)→game.get_building`, alongside unit/item/skill/region. A live game object *not* listed there falls through to the **generic `pickle` branch**, which on load deserializes a *stale copy* instead of the live registry singleton → turnwheel/load identity desync. Add the type to `save_obj`/`restore_obj` rather than storing the object raw.

**Building terrain override**: a placed building's `terrain` (a `BuildingPrefab` attribute) overrides the tile's terrain in the engine. Every terrain consumer funnels through one resolver, `game.get_terrain_nid(tilemap, pos)` (movement cost, opacity, sight, terrain status, `RequiresTerrain`), so the override lives there — precedence is **building > TERRAIN region > tilemap layer** (a building beats even a designer-painted TERRAIN region). The index is `game.building_terrain_overrides` (`Dict[Pos, NID]`, one entry per *footprint* tile, and none at all for a building that declares no `terrain` — see **Building footprints** below), maintained by `add_terrain_override`/`remove_terrain_override` (called from `AddBuilding`/`RemoveBuilding`) and `rebuild_terrain_overrides` (scans placed `city.buildings`; called from `load` and `start_level` **before** `set_up_game_board`, so the board's movement/opacity grids build with overrides already present). Because terrain status flows through `get_terrain_nid`, a building's terrain status skill applies automatically; the override is **non-destructive** (never mutates layer terrain) so removal restores the original, and layer changes (`ShowLayer`/`HideLayer`) happen underneath but a building still wins. 🔴 **Always read terrain via `game.get_terrain_nid(tilemap, pos)`, never `tilemap.get_terrain(pos)` directly** — the raw layer read silently skips both building overrides *and* designer TERRAIN regions. Several consumers had bypassed the resolver and showed the wrong terrain until fixed: `minimap.get_minimap_key`, combat platform + battle-background selection (`animation_combat.py`), and promotion platform (`promotion.py`). The resolver is the single chokepoint; a new terrain consumer that reads the layer directly is a bug.

**Building sprites (flat and recolored — NOT map animations)**: a building's `map_sprite_nid` resolves against `RESOURCES.building_sprites` (`app/data/resources/building_sprites.py`, a `map_icons`-shaped `ManifestCatalog`, listed in `Resources.save_data_types` **and** `optional_data_types` so a project with no `building_sprites/` folder loads an empty catalog). One flat PNG, 16 or 32 px a side — **no frames, no speed, no `MapAnimation`; buildings do not animate**. 🔴 **The recolor is the whole point.** Every sprite is drawn in one shared reference ramp held as a *project* combat palette under nid `building_ref`: **16 entries — the colorkey, then 13 map colors, then 2 team colors** (`building_palettes.NUM_MAP_COLORS`/`NUM_TEAM_COLORS`/`NUM_REFERENCE_COLORS`). The map colors are swapped per *tilemap* (`TileMapPrefab.building_style_nid` → another combat palette, chosen from the Building Style dropdown in the tilemap editor toolbar; only its first 13 non-colorkey colors are read), the team colors per *owning team* (`Team.building_color_primary`/`building_color_secondary`, raw `Color3`s backfilled in `TeamCatalog.add_defaults` from indices 8–9 of each team's `map_sprite_<color>` ramp — the backfill also runs for teams that already exist, or a project predating the fields keeps `None`). Both swaps go into **one merged conversion dict and one `color_convert` pass**, built by `app/data/resources/building_palettes.py::get_conversion_dict(style_nid, team_nid)` — deliberately **Qt-free and pygame-free** so the engine (`app/engine/building_sprite.py`, modeled on `unit_sprite.py`, cached in `game.building_sprite_registry` keyed `(sprite nid, style nid, team nid)` and cleared with the level) and the editor (`NewMapView.get_building_pixmap` via `editor_utilities.rgb_convert` + `color_convert_pixmap`) produce the identical table. Gotchas: 🔴 **`building.owner_nid` is the owning *city* nid, not a team** — get the team with `game.get_city(building.owner_nid).team`; a ramp that isn't exactly 16 entries logs an error (a short one slides the team colors onto the wrong reference entries and recolors *almost* correctly, which is near-invisible by eye); a missing style or missing `building_ref` degrades to the reference colors instead of crashing or drawing transparent. `building_model.get_pixmap` (the building catalog list) deliberately does **not** recolor — a catalog row has no map and no owner.

**Building footprints (`BuildingPrefab.size`)**: `Tuple[int, int]` in tiles, default `(1, 1)`, anchored at the **top left**; the sprite blits at the anchor tile's top-left corner and extends right and down over the rest. 🔴 **`size` is an explicit prefab field, never inferred from the sprite's pixel dimensions** — gameplay must know the footprint without loading art (headless tests, engine shipped without the editor). 🔴 **A 2x2 building is ONE `BuildingObject`, not four** — `building_system` city-aggregate hooks loop `city.buildings`, so four objects would pay `ResourcePerTurn` out four times. `BuildingObject.occupied_positions` / `positions_at(pos)` expand the footprint. Every footprint tile registers in **`game.building_position_index` (`Dict[Pos, UID]`)**, and *that* is what "this tile is occupied" means: 🔴 **never test occupancy with `pos in game.building_terrain_overrides`** — that dict only holds buildings that declare a `terrain`, so a terrain-less building read as free and two could be stacked on one tile (the bug this index fixed). Both indexes are maintained together by `add_terrain_override`/`remove_terrain_override`/`rebuild_terrain_overrides`, and removal is **uid-checked per tile** so a stale duplicate object can't evict the live building. `game.get_building_at(pos)` is the reverse lookup. `city_funcs.get_valid_placement_tiles` returns **anchor** tiles whose whole footprint is in bounds, inside the city's influence, and unoccupied. 🔴 **`target_restrict(building, city, position)` still receives the anchor only** — the correct quantifier differs per component, so each expands the footprint itself: `RequiresTerrain` demands *every* tile match, `RequiresAdjacency` accepts *any* footprint tile being adjacent (footprint-to-footprint, not anchor-to-anchor). Both are hand-written in `building_system_base.py`, so this needs no codegen change.

**City center, Seize and Raze**: the building carrying the marker component `CityCenter` (`nid='city_center'`, on the Outpost and the 2x2 Town Hall) *is* the city's center, and its components drive what the city does — don't move center/tier state onto `City`/`CityObject` fields. `CityObject.center` finds it; `center_positions` is its footprint (a city with no center building falls back to the single tile `city.position`). 🔴 **Ask `city.center_positions`, never compare against `city.position`** — `game.get_city_at(pos)` (AUX-open, tile-info panel), influence (`City.positions_within(radius)`, measured from the *nearest* center tile, center excluded) and `RequiresAdjacency` all go through it. `CityCenter.available` returns False, so a center building is never offered in the Build tab — a city gets its center at founding and a new one only by upgrade (both bypass `available` and `AddBuilding` directly). The level editor works on City *prefabs*, whose `center_positions` is just `[position]` (`app/data/cities.py` can't import `DB`: `database → levels → cities` would cycle), so `editor/map_view.py` has module-level `get_city_center_positions(city)` / `get_placement_positions(nid, pos)` that resolve footprints through `DB.buildings` + `BuildingPrefab.positions_at`; the city marker, selection outline and click-to-select all use them, so the marker sits where the *Town Hall placement* is, not at `city.position`. Taking a city is two `abilities.py` abilities offered while a unit stands on an enemy center with no enemy of its own anywhere on that center: **Seize** (heroes only, i.e. `not unit.generic`) → `action.ChangeCityTeam`; **Raze** (any unit) → `action.RazeCity`. Both fire immediately from the unit menu (no targeting state), end the unit's turn, then trigger `CitySeized` / `CityRazed`. 🔴 **A razed city is never removed from `game.city_registry`** — it gets `razed = True`, `game.cities` filters it out, and `game.get_city(nid)` still returns it. Deleting it would make every Action holding the city restore to `None` after a save/load (`restore_obj` resolves `('city', nid)` through `get_city`). Iterate `game.cities`, not `city_registry.values()`. `RazeCity` removes buildings last-first so reversing re-appends them in original order, rolls `raze_ruin_chance` (DB constant, percent) once per outlying building in `do()` and stores the result as sub-actions (`execute()` replays, never re-rolls), and paints `Terrain.RUINS` via `ChangeMapMakerTerrain` **only on a map_prefab-backed level** — a plain tilemap can't draw new terrain, so there buildings are just removed.

**Founding and carried food**: a hero (`not unit.generic`) founds a city with the **Found** ability (`abilities.py`, same immediate no-targeting shape as Seize/Raze) → `city_funcs.found_city` → `action.FoundCity`, then the `CityFounded` trigger. The new city starts as the building carrying the marker component `Outpost` (`city_funcs.get_outpost_prefab`), anchored top-left on the hero's tile. `can_found_city` requires the whole footprint in bounds, clear of `game.building_position_index`, at least the `city_min_distance` constant from every *live* city's center (nearest tile to nearest tile), and `building_system.target_restrict(outpost, city, anchor)` — so site rules are ordinary components on the Outpost (`RequiresTraversable` = every footprint tile costs < 99 in the mcost table for a named movement type; `RequiresTerrain` also works). Price is the Outpost's own `Cost`: **gold from the team, food from the hero** (production is not charged — a new city has no store). 🔴 **Hero food lives in items, not on the unit**: the `Food` item component (`usable_components.py`, modeled on `Uses`) keeps `item.data['food']` / `['starting_food']`; read it with `city_funcs.get_carried_food(unit)` and spend it with `spend_carried_food` (reversible `SetObjData`, first item emptied first). A food item that hits zero is used up: `Food` defines `is_broken`/`on_broken` like `Uses`, and `spend_carried_food` runs that check itself, since nothing outside combat calls it. **Outposts**: `CityObject.is_outpost` is true while the city's center carries `Outpost`. An outpost drafts nothing (`get_draftable_units` returns `[]`) and `get_buildable_buildings` offers it only buildings carrying `OutpostBuildable`, via the hand-written candidate hook `building_system.outpost_buildable(building, city)` — which defaults **False**, the opposite of `available`, because a building *lacking* a component cannot veto itself. **Upgrading** (Outpost → Town Hall, or any building carrying `UpgradesTo`): `city_funcs.get_building_upgrades(city)` returns a `BuildingUpgrade(old, new)` per target of every placed building's `UpgradesTo`, `new` being an unplaced candidate already anchored on `old`'s tile. The price is the *target's* `Cost`, paid like any purchase (team gold, the city's own food/production stores — not hero food) and it spends the city's one purchase for the turn. `action.UpgradeBuilding` is `RemoveBuilding` + `AddBuilding` and then moves the new building into the old one's index in `city.buildings` (both sub-actions append, so without that an upgrade — and its undo — would reorder the city). 🔴 An upgrade skips `available` (a center is never "available") but **does** honor `target_restrict` through `city_funcs.upgrade_fits`, so a site rule on the target can leave a building un-upgradable where it stands: a Town Hall with `RequiresTerrain` cannot replace an Outpost founded on other ground. The row is shown greyed rather than hidden. `build_unlock` tech gating applies to upgrade targets too. `FoundCity.reverse` deletes the city from `city_registry` outright (unlike a raze): the turnwheel truncates undone actions before any save, so nothing can restore a reference to it. 🔴 `action._refresh_building_terrain` must loop the building's **whole footprint** (`occupied_positions`) for both `board.reset_pos` and terrain-status refresh — it used to touch only the anchor, leaving three tiles of a 2x2 building with stale movement costs.

**City interaction (in-game)**: the player opens a city via **AUX over an owned city tile** (`FreeState.take_input`), *not* a unit action/ability — 4X cities aren't "operated" by a unit, and AUX works even when a unit occupies the center tile (SELECT there picks the unit). AUX is context-sensitive (owned city → open; else → cycle next unit). Because the control is otherwise hidden, the AUX key symbol is prefixed to the terrain name in the tile-info panel (`ui_view.create_tile_info`) whenever the hovered tile is a city you own — cities live on a dedicated "City" terrain, so the panel looks normal but advertises the control. The menu is `menus.CityMenu` (Draft/Build/Manage tabs) driven by `CityMenuState`. **Manage** is the tab for what a city does to itself rather than makes; today its only rows are building upgrades (`UpgradeBuildingOption`), so when a second kind of row arrives (give resources, build a road) the tab needs a row type that isn't a building. **Purchases are immediate**: selecting a Draft row pays gold/food/production and spawns the unit, carrying its class's `default_items`, next to the city already finished for the turn (`action.Wait`, built *after* `ArriveOnMap` so it snapshots the real position); selecting a Build row pays, then hands off to `PlaceBuildingState` via `next_state` + `transition_to_with_pop` (cursor constrained by `SelectionHelper` to `city_funcs.get_valid_placement_tiles`), which returns to the city menu the same way — backing out of placement refunds the full cost *and* the city's purchase for the turn. Both states live in **`app/engine/city_states.py`** (not `general_states.py` — keep new map states out of that already-huge file). 🔴 **`CityMenuState` is a full-screen `State` modeled on `InfoMenuState`, NOT a `MapState`** — a city needs the whole screen, so it sets `in_level = show_map = False`, builds a `background.PanoramaBackground` from the `city_menu_background` panorama in `start()`, then `game.state.change('transition_in'); return 'repeat'`, and draws its own bg in `draw()` (no map underneath). It is entered the same way as the info menu: the AUX handler sets `game.memory['next_state'] = 'city_menu'` and does `game.state.change('transition_to')` (a bare `change('city_menu')` skips the fade). Converting `MapState`→`State` **loses `self.fluid`** (only `MapState.__init__` makes one), so `CityMenuState.start` must build its own `FluidScroll()`. `PlaceBuildingState` stays a `MapState` (it drives the cursor on the map). `CityMenu` itself owns the full-screen layout (header row, food/production store counts with per-turn income, tab icons) — sub-`Choice`s pass `background=None` so the panorama shows through.

**Editor — components that need a multi-field table** (e.g. `ProducesUnits` = per-row `[class, level, gold, food, production]`): the component editor **can't** express this with the stock types. Inside `NewMultipleOptions` only `List` nests (`component_subcomponent_editors.CONTAINER_EDITOR_MAP == {List}`, and only types with a `DELEGATE_MAP` entry — no `Int` delegate, so `(List, Int)` fails); a top-level `(Dict, X)` gives only **one** int per key; and a component can't be duplicated on one prefab (`Data.append` keys by nid). A list-of-rows therefore needs a **bespoke `ComponentType`** wired through 4 places: the enum (`data/database/components.py`), a delegate (`editor/component_editor_delegates.py`), a list model (`extensions/list_models.py`, e.g. `PentaListModel(DoubleListModel)` — column-generic, override only `create_new`), and a widget + `get_display_widget` branch (`editor/component_database.py`). See the `UnitDraftList` implementation as the template. Separately, **non-`BOOL` constants don't auto-draw** in the Constants editor — `BOOL` ones auto-list by tag, but `INT`/`STR`/`MUSIC`/etc must be added by nid to a `create_section(...)` group in `editor/constant_tab.py` or they're invisible despite existing.

**In-game menu rows own their drawing** (general pattern, not 4X-specific): a menu is a list of `menu_options.*Option` instances that each implement `draw(surf,x,y)`/`width`/`height`/`get`/`get_help_box`; `menus.Choice` is the scroller. To make a `Choice` of custom rows, **subclass it and override `create_options`** to build your option class and set `option.help_box = option.get_help_box()` (see `CityChoice` + `DraftUnitOption`/`BuildingOption`/`WorkBuildingOption`). Don't reimplement scroll/cursor/help in the composite widget — delegate to the sub-`Choice`s (as `Convoy` and `CityMenu` do).

### Renown / Tech ("unlock") system (`avalon` branch, WIP)

A 4X progression layer sitting on the *existing* component machinery — **no 4th codegen system**. Design spec lives in `tech_system_notes.md`. A **Tech** owns no logic: it's a `TechPrefab` (`app/data/database/techs.py`, catalog `DB.techs`) = gating (`renown_cost`, `requires` prereq nids, `conditions` eval strings — all ALL-tested) + `components: Data[TechComponent]`.

🔴 **Tech effects are components, but there is NO generated `tech_system.py`.** `TechComponent` (`app/data/database/tech_components.py`) reuses the `Component` base, the `ComponentType` expose machinery and the whole component *editor* — but tech components are never hook-dispatched. They are read declaratively by `tech_funcs` and `action.UnlockTech`, so `source_generator.py` is untouched and there is no `*_HOOKS` table. The concrete components live in `app/engine/tech_components/base_components.py`; the catalog is `app/engine/tech_component_access.py` (`get_tech_components`/`get_tech_tags`/`restore_component`, a copy of `building_component_access`). Enums: `Combine` (`sum`/`max`/`set`/`or`) and `GrantTarget` (`team_units`/`units_with_tag`/`team_cities`/`self_team`), both now in `tech_components.py` — `techs.py` re-exports them, and importing them the other way round would cycle.

🔴 **A flag component owns its `flag_key` and `combine` as CLASS attributes** — the engine read site dictates the combine policy, so a designer cannot pick a wrong one (`sum` on `weapon_tier` was always a bug). `TechComponent.flags()` returns `[(key, value, combine)]`; a component whose key depends on its own value overrides it (`UpkeepCostReduction` → `'upkeep_cost_' + tag`, `ResourceBonus` → `f'{tag.lower()}_resource_bonus'`). Materialize-at-unlock components (`GrantSkillEffect`, `UpgradeItemsEffect`) leave `flag_key = None`, return `[]`, and are matched **by nid** in `action.UnlockTech`. `CustomFlag` is the escape hatch for a key whose read site exists but has no component yet (`dungeon_sight_bonus`, `hero_pool_tier`, `recruit_chance`, `elite_promote_<tag>`) — it types its value as a string and coerces int/float/bool on read.

🔴 **A `combine=SET` component's value is a LIST** (`DraftUnlock` = `(List, Class)`, `BuildUnlock` = `(List, Building)`), so one tech unlocks several classes. `_rebuild_flag_cache` and `city_funcs._tech_gated_values` must `update()`/`extend` from it, not `add` it. Likewise `GrantSkillEffect` holds `skills` (a **list**) for a single grant target — one tech can grant several skills, but not to several *different* targets; that would need a bespoke `ComponentType.GrantSkillList` rows table (template: `UnitDraftList`/`UnitDraftDelegate`/`PentaListModel`), which would **also** need branches in `get_objs_using`/`swap_values`, since a bare enum expose type isn't walked for nid renames the way a tuple one is.

**Legacy `effects` migration**: techs used to store a tagged-union `effects` list (`{kind: flag|grant_skill|upgrade_items}` with a free-text `key`). `TechPrefab.restore` maps that forward when `components` is absent (`_restore_legacy_effects`), so an old project loads unchanged and rewrites on the next save. Repeated set-flag keys on one tech merge into that component's list; an unrecognised key becomes a `CustomFlag`. The inline legacy cases in `app/tests/test_tech_system.py` (`LegacyEffectMigrationTests`) cover the migration.

🔴 **`DB.techs` is registered as an `optional_data_type`, NOT via a serialization version bump + migrator.** New DB data types added this way (mirrors `map_terrain_associations`): a project with no `techs.json` loads an empty catalog (the loader sets the key to `None` and `continue`s past the missing-file raise). Adding a migrator for a purely-additive catalog is the wrong tool.

**Two effect shapes, two costs** (the whole perf model): a **flag component** = a **single-site O(1) read** — the default; the engine reads `game.get_tech_value(team, key)` at one fork. `GrantSkillEffect`/`UpgradeItemsEffect` = **materialize at unlock** (pay once at a cold state-change, zero per-hook cost after). **Never** gate global skills on a re-evaluated `condition` — that's the expensive path the whole design avoids.

**Runtime state on `TeamObject`** (`app/engine/objects/team.py`): `renown: int` (+ save/restore), `research: List[str]` (unlocked tech nids — already existed), `_tech_flag_cache` (**not serialized**; `{key: combined_value}` rebuilt lazily on read). `app/engine/tech_funcs.py` is the interpreter (no codegen): `has_tech` / `get_tech_value(default=0)` / `get_tech_set` (returns a copy) / `can_unlock` / `_rebuild_flag_cache` / `invalidate_flag_cache` + collection helpers (`unit_matches_grant_target`, `get_grant_target_units`, `get_tech_skills`). `get_tech_value` reads the precomputed dict — T1 reads are a lookup, not a scan.

🔴 **`game.has_tech`/`get_tech_value`/`get_tech_set`/`get_renown` use a *lazy* `from app.engine import tech_funcs` inside each method** — a module-level import cycles (`game_state → tech_funcs → evaluate → combat_calcs → game_state`, and `game` isn't bound yet). This is consistent with game_state's house style (it lazy-imports ~30 engine modules for exactly this reason); the hub is *the* exception to the module-level-import rule. `tech_funcs` and `action.py` themselves import at module level (no cycle). All four accessors take a **team nid or a live `TeamObject`** (`_resolve_team`).

**Actions** (`action.py`, all reversible/turnwheel-safe): `ChangeRenown(team, amount)`; `UnlockTech(team, tech_nid, free=False)`; `UpgradeItem(unit, item, new_item_nid)`. `UnlockTech` builds reversible sub-actions (`ChangeRenown(-cost)`, an `AddSkill` per skill per `GrantSkillEffect` target unit, a `UpgradeItem` per upgradeable item) and is **idempotent** (already-owned → no-op). It is **NOT gated on `can_unlock`** — the caller/UI gates (the `unlock_tech` event command force-unlocks for scripting). `free=True` omits the `ChangeRenown(-cost)` sub-action entirely, for story unlocks the player didn't buy. 🔴 **`UnlockTech._record()` (append nid to `research` + `invalidate_flag_cache`) runs BEFORE the effect sub-actions are built/executed** — tier-dependent effects (`UpgradeItemsEffect` reading `weapon_tier`, the sight re-reveal reading `overworld_sight_bonus`) must see the *new* flag value. Building them before recording reads the stale (pre-unlock) tier and silently under-upgrades. `execute()` (turnwheel redo) replays stored sub-actions after `_record`; `reverse()` removes the nid, reverses sub-actions, re-invalidates.

**GrantSkillEffect plumbing** — the skills ride per-unit through combat/skill machinery. Materialized **twice, identically**: (1) at unlock, `UnlockTech` `AddSkill`s it onto every current `get_grant_target_units` unit; (2) on unit **construction**, `unit.py` adds `tech_funcs.get_tech_skills(self)` (sibling of `unit_funcs.get_global_skills`) so future/drafted units get it. **Both paths use `source='game', source_type=SourceType.GLOBAL`** — non-removable/non-displaceable game-rule skills that serialize normally (only `AURA` is filtered from `UnitObject.save`, so no re-derivation on load; turnwheel still removes them because `AddSkill.reverse` is authoritative).

**Event commands** (`app/events/`): `add_renown;<team>;<amount>` (negative allowed) and `unlock_tech;<team>;<tech>[;free]`, implemented in `event_functions.py` as `add_renown` / `unlock_tech` (dispatch is by function name == command nid) with a `Tech` validator over `DB.techs` in `event_validators.py`. Adding a command means adding all three — the suite's `test_check_event_functions_match_event_commands` asserts the class name camel-to-snakes to the nid and that the function signature is `(self, *keywords, flags=None)` in keyword order — then rerunning `python -m app.engine.codegen.source_generator` to regenerate the python-eventing wrappers (`python_event_command_wrappers.py`, gitignored).

**`weapon_tier` retroactive weapon upgrade** — the mapping lives on the *item*, not the tech: an `UpgradesTo` item component (`extra_components.py`, `{target_item, required_tier}`) declares the chain (Iron→Steel→Mithril). `item_funcs.resolve_upgrade_nid(item_nid, tier)` walks it (cycle-guarded) to the highest item the team's `weapon_tier` unlocks. A `WeaponTier` component sets the tier; a **separate** `UpgradeItemsEffect` component on the same tech triggers the physical sweep (kept separate so you can raise tier without a sweep, or re-sweep). `UpgradeItem` swaps in-place preserving slot/droppable/remaining-uses (clamped to new max) and relies on `@recalculate_unit` autoequip. Two sites like GrantSkillEffect: unlock sweep + construction resolve (`resolve_upgrade_nid_for_team`). Convoy/map-loot are **not** swept (only `GrantTarget` inventories + newly-built units).

**Editor** — `app/editor/tech_editor/` (`new_tech_tab.py` + `tech_model.py`), registered by one entry in the `database_actions` dict in `main_editor.py`. `NewTechProperties` subclasses **`NewComponentProperties`** (so the whole component toolbar / search dialog / row rendering is inherited) and adds renown cost, a `MultiSelectComboBox` of prereq techs, a `find_prereq_cycle` warning label, and a `conditions` list using the new `EvalStringDelegate` (a `CodeLineEdit` in column 0 — every other single-list delegate hardcodes a catalog `ComboBox`). 🔴 **A `*_properties` widget reads the module-global `DB`, not the tab's `self._db`** — that's the house style across class/unit/skill properties, so a test must drive the global `DB` singleton or the dropdowns read a different catalog than the tab. Wiring added for tech components and reusable elsewhere: `TagSubcomponentEditor` in `EDITOR_MAP` (`NewMultipleOptions` had no Tag field editor) and `BuildingDelegate` in `DELEGATE_MAP` + `get_display_widget`'s tuple branch (`(List, Building)` previously fell through with `delegate=None`). A tag with no `component_<tag>.png` icon now renders its toolbar button as text instead of a blank square — that also fixes Buildings, whose `resource`/`unit` tags never had icons.

**Phase-4 flag-read integration sites** (each is one `game.get_tech_value`/`get_tech_set` at a natural fork):

| Tech key | Combine | Read site |
|---|---|---|
| `exp_mult_bonus` | sum | `SimpleCombat.calculate_exp` (`total_exp *= 1 + bonus`) |
| `road_move_bonus` | max | `movement_funcs.get_mcost` (needs `terrain.road` bool; road's `mtype` is `Normal`, not a distinct type) |
| `city_pop_bonus` | sum | two sites, like `grant_skill`: `action.UnlockTech` matches the component **by nid** and tops up every city the team already owns (reversible `ChangeCityPopulation` sub-actions), and `CityObject.from_prefab` reads the flag so a city built later starts with the bonus. Renamed from `city_pop_cap_bonus` (there is no population cap); `_LEGACY_FLAG_COMPONENTS` maps the old key onto it |
| `draft_unlock` / `build_unlock` | set | `city_funcs` gating via `_tech_gated_values(key)` — a class/building nid mentioned in **any** tech's set-flag is locked until that team unlocks it; nids never mentioned stay unconditional |
| `farm_/mine_/artisan_resource_bonus` | sum | `ResourcePerTurn.get_output` via the `BuildingTag` component + `RESOURCE_BONUS_TAGS` map |
| `upkeep_cost_<tag>` | sum | `city_funcs.get_unit_upkeep` — sums each living team unit's `klass.upkeep_cost`, reduced per-unit per tag; run per-team on that team's phase from `status_upkeep` |
| `overworld_sight_bonus` | max | `game_board.get_fog_of_war_radius` (see Fog section) |

`BuildingTag` (`building_components/base_components.py`, `nid='building_tags'`) mirrors `ItemTag` — `expose=(List,Tag)`, no dispatch hooks, `BuildingObject.tags` reads it like `ItemObject.tags`. `klass.upkeep_cost`, `klass.default_items` and `terrain.road` are **bespoke typed dataclass fields** (like `max_level`/`tier`), not entries in the generic `fields` bag — first-class always-evaluated mechanics belong in the typed schema. 🔴 **Construct a `Klass` with keyword arguments.** It is a dataclass, so a new field in the middle shifts every positional argument after it: adding `upkeep_cost` silently broke `ClassCatalog.create_new` and `class_import` (a new class got a dict for its upkeep and a list for its max stats). `default_items` is `[item_nid, droppable]` rows, the same shape as a unit's `starting_items`, so the class editor reuses `ItemListWidget` and `city_funcs.draft_unit` hands copies of the rows straight to `GenericUnit` — a class with none drafts an unarmed unit. The item editor's rename and delete-swap walk `DB.classes` for it (`Klass.replace_item_nid`).

### Level editor map view (`app/editor/map_view.py`)

`NewMapView` repaints the whole tilemap + overlays every tick: `level_editor.py` wires `timer.get_timer().tick_elapsed → map_view.update_view` (~30fps). **So map overlays animate for free — don't add a per-widget `QTimer`.** To animate a sprite, just pick the current frame inside the paint method from a shared clock (unit sprites use `timer.get_timer().passive_counter.count`). `update_view` dispatches on `edit_mode` (`EditMode.UNITS/REGIONS/CITIES/GROUPS/…`) to a `paint_*` method; the active tab sets the mode via its dock visibility callback (`level_editor.py::on_*_tab_select`). **Gotcha: `MapAnimation.pixmap` is lazy** — `None` until something assigns `QPixmap(res.full_path)`, so a paint path that draws a map anim must lazy-load the pixmap itself (`PushableMapAnimation.render` does) or sprites stay blank until the resource editor loads them. Buildings no longer go through this — they are flat sprites, see **Building sprites** above.

### Fog of war / sight

Board vision is precomputed state in `game_board.fog_of_war_grids`, mutated **only** by `update_fow` / `change_sight_range` (driven by the `UpdateFogOfWar` action). `game_board.fow_vantage_point[unit.nid]` is the tile a unit "sees from". A unit's sight is `skill_system.sight_range(unit) + fog radius`, and `sight_range` is gated by component `condition`, so a terrain-conditional sight bonus changes with `unit.position`. **Gotcha: during a move preview the vantage stays at the unit's start tile — a unit must not reveal new vision until it Waits** (`Wait.do` → `UpdateFogOfWar` moves the vantage and applies full sight; cancelling instead reverses the move). `action.recalc_unit` (fired by the `@recalculate_unit` decorator on `AddSkill`/equip/terrain-status/etc.) must therefore only refresh sight when `unit.position == fow_vantage_point[unit.nid]`. Refreshing mid-move applies the conditional sight bonus at the *stale* vantage (revealing tiles from the start position) and — because it writes straight to the board rather than as a reversible action — that change survives cancelling the move.

**`game_board.get_fog_of_war_radius(team)` is the per-team sight additive chokepoint** — every board-sight computation is `skill_system.sight_range(unit) + get_fog_of_war_radius(team)` (recalc, `UpdateFogOfWar` do/reverse, LOS). A **per-team** sight tech (`overworld_sight_bonus`) therefore adds one line *there*, NOT in `skill_system.sight_range` (which is per-unit, component-driven, and **codegen'd** — wrong altitude and clobbered on regen). Board vision is cached, so to reveal *the instant* a sight tech unlocks (not just on next move), `UnlockTech` appends a reversible `UpdateFogOfWar` per on-field team unit when `_fog_of_war` is active.

## Conventions

- Objects are referenced by string ids: **NID** (named id, design-time, stable across a project) and **UID** (unique id, runtime instance). Types in `app/utilities/typing.py`.
- Shared, framework-agnostic helpers live in `app/utilities/` (no Qt, no pygame deps) — prefer reusing `utils.py`, `str_utils.py`, `static_random.py` (deterministic RNG for turnwheel/replays) over rolling your own.
- The engine must stay importable without PyQt5 (it ships as a standalone executable); keep editor-only imports out of `app/engine`.
- **Whose turn it is** (`phase.py::PhaseController.next`): teams go in `DB.teams` order; a team is skipped unless it `_takes_part` — has a unit on the map or owns a live city — except the player, who is never skipped. (A city counts because `StatusUpkeepState` is where its income and its purchase for the turn come from; skipping the phase skipped both.) `FreeState.begin` then ends the player's turn by itself (the `autoend_turn` setting) once no selectable player unit is unfinished. Two things hold that off: the player having **no** unit on the map ("none unfinished" was instantly true, so the turn ended itself forever), and any player city that can still buy this turn (`city_funcs.can_purchase`) — whether or not it can afford anything, so a player with cities ends such a turn from the menu.
- A MAJOR_FEATURES DB constant (e.g. `support`, `fatigue`) is usually **not** the runtime gate — it enables the feature in the editor/UI. The actual runtime switch is a `_`-prefixed game var (`_supports`, `_fatigue`, `_convoy`, `_turnwheel`) set via an event command (e.g. `game_var;_supports;True`), often deliberately deferred to a story beat. When gating engine behavior on a feature, check the game var, and check it in **every** path (combat, info menu, accumulation, etc.) — a missing check in one path leaks the feature inconsistently.
- Tests live in `app/tests/`, mostly engine/data/event coverage (the editor is largely untested). **Tests cover engine and editor code only, never a particular game's content or rules** — a game's own events and data (Avalon's elimination events, its tech list) are checked by hand or a throwaway script, not in this suite. The full suite takes minutes: while iterating, run only the test modules for what changed (`python utilities/build_tools/run_tests_parallel.py test_x test_y`) and run everything once before a commit. Several tests load the sample `.ltproj`s, so don't break their data integrity (`test_base_project_integrity.py`).
- **Engine tests: subclass `EngineTestCase` from `app/tests/engine_harness.py`.** It resets the globals below per test (headless display, project reload, sprites reloaded *after* `RESOURCES.load` resets them, default settings instead of the developer's config, pinned seed, fresh `game`). `self.start_harness()` returns an `EngineHarness` that plays a level through the real state machine with a fake clock and scripted key presses (the phase banner is cut short: `EngineHarness` patches `PhaseIn.update` to report the banner finished at once, since its 87 frames at every phase change were a third of these tests' time — a phase still starts for real, only the animation is skipped) (`start_level`, `press`, `move_cursor_to`, `choose`, `wait`, `attack`, `run_until_player_turn`, `round_trip`). Prefer it to mocking `game` for state-machine bugs; `test_save_round_trip.py` uses it for save/load.
- Tests share the **global `game` singleton** (`game_state.py::game`); its state leaks across tests within a run. A test that touches `game` must seed everything it reads (e.g. `game.game_vars = PrimitiveCounter()`, `game.target_system = …`) in `setUp` or its helper — never rely on what a prior test left behind, or you get order-dependent pass/fail that only shows up in the full suite, not when the test runs alone.
- 🔴 The same leak bites **module-level sprite reads**. `app/engine/settings.py` builds its `controls`/`config_icons` dicts from `SPRITES.get(...)` at import time, and another test resetting the sprite dict (without re-running `sprites.load_images()`) leaves every entry's `.image` as `None` → `AttributeError: 'NoneType' object has no attribute 'get_size'`. **`RESOURCES.load` itself resets the sprite dict** (to pick up a project's custom sprites), so images must be loaded *after* it. `EngineTestCase` does this, and `engine_harness` imports every state module when test discovery imports it (before any test can unload the sprites), since a module first imported while sprites are unloaded keeps `None` in its class attributes (e.g. `menus.Trade.trade_name_surf`) for the rest of the run. Outside it, call `app.engine.sprites.load_images()` in `setUp` after any `RESOURCES.load` and before importing such a module. Passes alone, fails in the suite.
- 🔴 **`DB.constants` survives `DB.load`.** `ConstantCatalog.restore` only assigns the values a project's `constants.json` lists; a constant the file doesn't mention keeps whatever value it had — including one a previous test set. A test that calls `DB.constants.get(nid).set_value(...)` on a constant missing from `testing_proj` must restore it (`self.addCleanup(constant.set_value, constant.value)`), or the change leaks into every later test (`city_min_distance` did exactly this).
- A `patcher.start()` in `setUp` needs a matching stop (`self.addCleanup(patcher.stop)`). A forgotten one replaces the target for **every later test in the run** — `test_add_remove_skills` once left `action.ResetUnitVars` faked for the rest of the suite.
- **Editor code is testable headlessly** despite being Qt-heavy: `from app.tests import qt_headless` (sets `QT_QPA_PLATFORM=offscreen`, points the offscreen font database at the system fonts, drops the offscreen-only `propagateSizeHints()` warning) before the first `QApplication(sys.argv)` is enough to exercise models, dialogs' logic (patch `QFileDialog`/`QInputDialog`), and QPixmap work. For anything that writes, `shutil.copytree('default.ltproj', tmp)` first and load *that* — never experiment against the sample projects in-tree.
- On Windows, Qt sends its warnings (`qWarning`, e.g. `QSettings:`/`QFontDatabase:` messages) to the debugger rather than stderr when the process has no console, which includes an agent's shell. Set `QT_FORCE_STDERR_LOGGING=1` to see what a developer's terminal shows.
- 🔴 Never fingerprint a QPixmap via `pixmap.toImage().bits()`: the intermediate `QImage` is a temporary that Python frees immediately, so the buffer is garbage and comparisons produce **false differences**. Keep the `QImage` in a variable and compare `QImage` objects directly (`im1 != im2`).
